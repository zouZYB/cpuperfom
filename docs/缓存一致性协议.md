## 一、CPU 缓存基础

### 1.1 为什么需要缓存

CPU 运算速度远超内存访问速度(相差约 100~200 倍),即"内存墙"(Memory Wall)问题。缓存利用**局部性原理**缓解矛盾:

- **时间局部性**:刚访问过的数据很可能再次被访问(循环变量)
- **空间局部性**:相邻数据很可能一起被访问(数组顺序遍历)

| 存储层级 | 典型访问延迟 | 类比 |
|---------|-------------|------|
| 寄存器 | < 1 个时钟周期 | 手上的笔 |
| L1 缓存 | 4~5 周期 | 桌上的纸 |
| L2 缓存 | 12~15 周期 | 书架 |
| L3 缓存 | 40~70 周期 | 楼下仓库 |
| 主内存 | 200~300+ 周期 | 跨城市取货 |
| SSD/磁盘 | 数十万个周期 | 跨国海运 |

查找顺序:L1 → L2 → L3 → 内存,逐级变慢。L1/L2 每核独占,L3 多核共享(或按 Cluster/CCX 共享)。

### 1.2 缓存行(Cache Line)

- 缓存读写的最小单位,主流 x86/ARM 均为 **64 字节**
- 读 1 字节 = 加载整个 64 字节行
- 缓存行结构:`[ Tag(地址标签) | 状态位(MESI 等) | Data(64 字节) ]`
- 物理地址划分:`[ Tag | Set Index | Line Offset(6 bit, 2^6=64) ]`

### 1.3 组相联结构

- **直接映射**:每个地址只能放一个固定位置,冲突严重
- **全相联**:任意行放任意位置,硬件成本高
- **组相联(主流,4~16 路)**:地址定位到组(Set),组内 N 路(Way)并行比较 Tag

相联度越高冲突不命中越少,但查找电路越复杂、功耗越高。

### 1.4 缓存不命中的 3C 模型

1. **Compulsory(强制)**:首次访问必然不命中 → 用预取缓解
2. **Capacity(容量)**:工作集超过缓存大小 → 循环分块(Tiling)
3. **Conflict(冲突)**:不同地址映射到同一组互相驱逐 → 避免 2 的幂次步长

### 1.5 写策略

| 场景 | Write-Back(主流) | Write-Through |
|------|------------------|---------------|
| 写命中 | 只改缓存,置脏位,换出时才写内存 | 同时写缓存和内存 |
| 写不命中 | Write-Allocate:先读入行再写 | 可选 No-Write-Allocate 直写内存 |

## 二、缓存一致性问题

多核系统中同一内存地址可能同时存在于多个核心的私有缓存中:

```
Core0 L1: X=5  (刚写入)
Core1 L1: X=3  (旧值,不一致!)
```

一致性协议的两种基本思路:

1. **Write-Invalidate(写失效,主流)**:写入时使其他副本失效,节省带宽
2. **Write-Update(写更新)**:写入时广播新值给所有副本,带宽消耗大

维护机制:

- **总线嗅探(Snooping)**:所有核心监听共享总线(中小规模)
- **目录协议(Directory)**:集中式目录记录每行的持有者(大规模服务器、NUMA)

## 三、MESI 协议

### 3.1 四种状态

每个缓存行用 2 个状态位标记:

| 状态 | 名称 | 含义 | 内存是否最新 | 其他核心是否可能有副本 |
|------|------|------|-------------|----------------------|
| **M** | Modified 修改 | 被本核心修改过(脏) | 否 | 否(独占) |
| **E** | Exclusive 独占 | 干净,只有本核心持有 | 是 | 否 |
| **S** | Shared 共享 | 干净,多核心可能都有 | 是 | 是 |
| **I** | Invalid 无效 | 不可用 | — | — |

**E 状态的核心价值**:E→M 是静默转换,无需总线广播。单线程程序大量受益于此。

### 3.2 状态转换

本核心操作:

| 当前状态 | 本核心读 | 本核心写 |
|---------|---------|---------|
| M | 命中,不变 | 命中,不变 |
| E | 命中,不变 | E→M(无总线消息) |
| S | 命中,不变 | S→M(广播 Invalidate,即 RFO) |
| I | 未命中,总线读 → E 或 S | RFO → M |

嗅探到其他核心的总线事务:

| 当前状态 | 听到别人读(BusRd) | 听到别人写(RFO) |
|---------|-------------------|----------------|
| M | 先写回/供出数据,M→S | 先供出数据,M→I |
| E | E→S | E→I |
| S | 不变 | S→I |

## 四、RFO(Read For Ownership)

### 4.1 定义

**RFO = Read For Ownership(所有权读取)**,也写作 **BusRdX**(带修改意图的总线读)或 Read-Invalidate。核心要**写**某行但当前状态不是 E/M 时发出的组合请求:

1. **读(Read)**:获取该缓存行的最新数据
2. **取得所有权(For Ownership)**:广播要求其他所有核心把副本置为 I,自己独占进入 M 状态

| 当前状态 | 写入需要的操作 |
|---------|---------------|
| M | 直接写,无总线事务 |
| E | E→M 静默转换,无总线事务 |
| S | 发 RFO:其他副本→I,自己 S→M |
| I(写不命中) | 发 RFO:读入数据 + 失效其他副本 → M |

### 4.2 完整握手过程

```
Core0 要写 X(当前 S 状态,Core1 也有副本):

Core0 ──RFO(X)──→ 总线/互连
                     ├─→ 内存:提供 X 的最新数据(或由缓存转发)
                     └─→ Core1:收到 Invalidate,X 置为 I,回复 ACK

Core0 收到:数据 ✓ + 全部 ACK ✓ → X 进入 M 状态 → 执行写入
```

### 4.3 性能意义

- **RFO 是多核写入开销的主要来源**:广播 + 等 ACK + 缓存间传输,延迟可达上百周期
- **Store Buffer 就是为隐藏 RFO 延迟而生**
- **伪共享(False Sharing)的本质**:两个核心反复写同一缓存行的不同变量 → 缓存行在两核间反复 RFO 往返(ping-pong)
- 解决伪共享:按缓存行对齐填充(C++ `alignas(64)`,`std::hardware_destructive_interference_size`)

## 五、MESIF 协议(Intel)

### 5.1 为什么需要 MESIF

MESI 中,一行处于 S 状态(多核共享)时,读请求由**内存**供数。问题:

- 缓存中有干净副本时,**缓存到缓存传输**比访问内存更快(尤其 NUMA 系统,数据可能在远端内存)
- 所有共享者同时响应会造成混乱

Intel 从 Nehalem(2008)起在 QPI/UPI 互连架构中使用 MESIF,特别适用于多路服务器。

### 5.2 F 状态(Forward)

| 状态 | 名称 | 含义 |
|------|------|------|
| **F** | Forward 转发 | 干净、共享,但**被指定为应答者**:其他核心读该行时由 F 持有者直接转发数据,内存不响应 |

- 一行最多只有一个核心持有 F,其余共享者为 S
- F 和 S 本质相同(干净共享),区别仅在"谁负责转发"
- **最新请求者成为新的 F**(刚读过的核心很可能还要用)

### 5.3 工作流程示例

```
初始:Core0 以 E 状态持有行 X

1. Core1 发出 BusRd(X)
   → Core0: E→F;Core1: 获得数据,进入 S

2. Core2 发出 BusRd(X)
   → Core0(F)转发数据,F→S(交出转发权)
   → Core2: 获得数据,以 F 状态进入

3. Core2 想写 X → 发出 RFO,F→M,其他副本→I
```

### 5.4 关键问题:会存在"有 S 但没有 F"的情况吗?

**会。** 标准事务路径维持"存在共享副本 ⟹ 恰好一个 F"的不变式,但**静默替换**会打破它:

```
时刻 T0:Core0=F, Core1=S, Core2=S
          ↓ Core0 缓存满了,F 行是干净行,被静默逐出(不回写、不广播)
时刻 T1:Core0=I, Core1=S, Core2=S   ← 有 S,没有 F
```

**为什么不出错**:F 是纯粹的**性能优化状态**,不承担正确性责任。F 行干净、内存最新,丢失后由内存(Home Agent)兜底供数,退化为普通 MESI 行为。实现上有两种策略:

- **补救**:F 逐出时发通知,由 Home 指定某个 S 提升为 F
- **容忍**:不处理,下次读走内存路径

**对比:F→M 时为什么没有这个问题?**

F 持有者写入时必须先发 RFO,把所有 S 副本置 I——F 和 S 同归于尽,最终是"一个 M,没有共享者"。不变式是条件式("**若**有 S 则必有唯一 F"),不是"任何时刻都有 F"。

| 场景 | 结果状态 | 有 S 无 F? | 不变式 |
|------|---------|-----------|--------|
| F 持有者写入 | 一个 M,其余全 I | 否(S 已被失效) | 成立 |
| F 持有者静默逐出 | 无 F,若干 S | 是 | 被打破(但被容忍) |

**F 的生命周期循环**:

```
E 被读 → 诞生 F
F 被第三方读 → F 转移给新请求者
F 写入 → F 消灭(连同所有 S)
F 静默逐出 → F 消失,S 裸存(协议容忍)
M 行被读 → 重新诞生 F(M→S,请求者→F)
```

## 六、MOESI 协议(AMD)

### 6.1 为什么需要 MOESI

MESI/MESIF 处理**脏数据共享**效率不高:

```
Core0 以 M 状态持有脏行 X,Core1 发出 BusRd(X)
```

MESI 的处理:Core0 必须先**写回内存**,Core1 再从内存读,双方进入 S。产生一次本不必要的内存写回;若 Core0 之后还要改,又会反复写回。

AMD 的思路:**允许脏数据在缓存间直接传递,不必先写回内存**。

### 6.2 O 状态(Owned)

| 状态 | 名称 | 含义 |
|------|------|------|
| **O** | Owned 拥有 | **脏数据,可共享**:本缓存行已修改(与内存不一致),但允许其他核心以 S 状态持有副本;**由 O 持有者负责最终回写内存** |

### 6.3 与 MESI 的关键差异

| 对比项 | MESI | MOESI |
|-------|------|-------|
| M 行被别人读 | 写回内存,M→S | **直接转发数据,M→O**,请求者→S,**不写内存** |
| 脏行被替换时 | M 回写 | **O 持有者回写**(唯一责任方) |
| 内存带宽 | 共享脏行场景浪费 | 节省(整个共享期间可能零内存流量) |
| 状态位 | 2 bit | 3 bit(5 状态) |

O 与 F 的责任对比(重要):

| 状态 | 数据是否干净 | 责任 | 能否静默丢弃 |
|------|-------------|------|-------------|
| **F**(MESIF) | 干净,内存最新 | 仅"谁转发"的优化职责 | 可以(内存兜底) |
| **O**(MOESI) | 脏,内存过时 | **必须负责回写** | **不可以**(丢了数据就没了) |

> 一句话:**F 可以丢,因为内存兜得住;O/M 不能丢,因为内存兜不住。**

### 6.4 应用

AMD 从 Opteron 时代起使用 MOESI 及变体,配合 HyperTransport / Infinity Fabric 互连;现代 CPU 的实际协议是更复杂的混合形态(如 MOESIF、带目录的探测过滤器等)。

## 七、Store Buffer 与 Invalidate Queue

### 7.1 动机:MESI 的两个性能痛点

1. **写等待(Store Stall)**:写 S/I 行需发 RFO 并等所有 ACK,期间 CPU 空等上百周期
2. **失效等待(Invalidate Stall)**:收到 Invalidate 的核心若缓存正忙,处理延迟会拖累发送方

### 7.2 Store Buffer(存储缓冲)

每个核心私有的 FIFO 队列,位于执行单元与缓存之间:

```
写流程:store → 记入 Store Buffer → 发出 RFO → CPU 立即继续执行
        后台收齐 ACK 后,条目刷入(drain)L1,进入 M 状态
```

**Store Forwarding**:load 查找顺序为 Store Buffer → L1 → L2 → L3 → 内存,保证本核心读到自己的最新写。

**代价:Store→Load 乱序**。Litmus test:

```c
// 初始:x = 0, y = 0
// Core 0                  // Core 1
x = 1;                     y = 1;
int a = y;                 int b = x;
// 结果可能 a=0 且 b=0!双方的写都"藏"在各自 Store Buffer 里
```

**x86 TSO 唯一允许的乱序**。解决:写屏障(排空 Store Buffer)——`MFENCE` / `LOCK` 前缀。

### 7.3 Invalidate Queue(失效队列)

接收方缓冲:收到 Invalidate 先**入队并秒回 ACK**,空闲时才真正置 I。

**代价:读到过期数据(Stale Read)**——核心已 ACK(承诺失效)但旧数据还在缓存里:

```c
// 初始:x = 0, flag = 0
// Core 0                       // Core 1
x = 1;                          while (flag == 0) { }
smp_mb();  // 排空 Store Buffer  smp_rmb();  // 必须!处理 Invalidate Queue
flag = 1;                       int a = x;  // 否则可能读到旧值 0
```

x=1 的 Invalidate 可能还躺在 Core1 的队列里没处理 → load 命中 S 状态的旧副本。

### 7.4 总结对比

| 结构 | 解决的痛点 | 引入的问题 | 对应屏障 |
|------|-----------|-----------|---------|
| Store Buffer | 写等 ACK 停顿 | 写对其他核心延迟可见(Store→Load 乱序) | 写/全屏障(排空) |
| Invalidate Queue | 失效处理拖慢 ACK | 读可能命中未失效旧行(Load→Load 乱序) | 读屏障(清空队列) |

各架构现实情况:

- **x86-64 (TSO)**:Store→Load 乱序真实可见;Load→Load、Load→Store、Store→Store 天然有序(不暴露 Invalidate Queue 乱序)
- **ARM / RISC-V(弱序)**:两种乱序都可见,屏障是并发编程必需品

**两个必须分清的概念**:

- **缓存一致性(Coherence)**:MESI 管的事——**同一个地址**最终一致(有 Buffer 也成立)
- **内存一致性模型(Consistency Model)**:跨地址的操作顺序——被 Buffer 破坏,需屏障约束

## 八、std::memory_order 与内存屏障

### 8.1 定位:语言层抽象 vs 硬件层实现

```
C++ 源码:  std::memory_order_acquire / release / seq_cst ...
                    │  编译器决定:
                    │  ① 禁止哪些编译器指令重排(编译器屏障)
                    │  ② 生成哪些硬件屏障指令(CPU 屏障)
                    ▼
汇编指令:  x86: LOCK 前缀 / MFENCE    ARM: DMB / LDAR / STLR
                    ▼
硬件行为:  约束 Store Buffer / Invalidate Queue / 乱序执行
```

### 8.2 六种 memory_order

| order | 语义 | 典型用途 |
|-------|------|---------|
| `relaxed` | 只保证原子性,不保证顺序 | 计数器、统计量 |
| `consume` | (不推荐,编译器按 acquire 实现) | — |
| `acquire` | 读:之后的读写不许重排到它之前(向前关门) | 读标志位、加锁 |
| `release` | 写:之前的读写不许重排到它之后(向后关门) | 发布数据、解锁 |
| `acq_rel` | acquire + release | 读改写操作(CAS) |
| `seq_cst` | 全局唯一顺序(默认,最贵) | 拿不准时保底 |

### 8.3 acquire + release 配对 = 消息传递

```cpp
// 生产者                        // 消费者
data = 42;                      while (!flag.load(acquire)) { }
flag.store(true, release);      assert(data == 42);  // 永远成立
```

- `release` 摁住生产者:data 先于 flag 全局可见
- `acquire` 摁住消费者:看到 flag 后,读 data 不会命中缓存旧值

### 8.4 memory_order → 屏障指令映射(GCC/Clang 典型生成)

| C++ 操作 | x86-64 | ARM64 |
|---------|--------|-------|
| `load(relaxed)` | `MOV` | `LDR` |
| `load(acquire)` | `MOV`(**零开销**) | `LDAR` |
| `store(release)` | `MOV`(**零开销**) | `STLR` |
| `store(seq_cst)` | `MOV` + `MFENCE`(或 XCHG) | `STLR` + 配对约束 |
| `fetch_add(seq_cst)` | `LOCK XADD` | `LDADDAL` |
| `fence(seq_cst)` | `MFENCE` | `DMB ISH` |

**x86 上 acquire/release 零开销的原因**:TSO 天然保证 Load→Load、Load→Store、Store→Store 有序;唯一允许的 Store→Load 乱序恰好是 acquire/release 不需要禁止的。x86 上 acquire/release 的全部作用是**阻止编译器重排**。

x86 上唯一真正产生硬件开销的 memory_order 是 **seq_cst 的 store**(需要 `LOCK`/`MFENCE` 阻止 Store Buffer 乱序)。

### 8.5 独立 fence 与附加 order

```cpp
// 方式一:order 附加在操作上(推荐)
flag.store(true, std::memory_order_release);

// 方式二:独立 fence
data = 42;
std::atomic_thread_fence(std::memory_order_release);
flag.store(true, std::memory_order_relaxed);
```

`std::atomic_signal_fence` 只做编译器屏障,`std::atomic_thread_fence` 做编译器+硬件屏障。

### 8.6 选型速查

| 场景 | 推荐 order |
|------|-----------|
| 计数器、统计 | `relaxed` |
| 标志位 + 数据发布 | 写 `release` / 读 `acquire` |
| 拿不准、先求正确 | `seq_cst`(默认) |
| 无锁数据结构极致优化 | 混合 `relaxed` + 精确 fence |

## 九、完整知识闭环

```
① CPU 与内存的速度鸿沟 → 引入多级缓存(以 64B 缓存行为单位)
        ↓
② 多核私有缓存 → 同一地址多副本 → 一致性问题
        ↓
③ MESI / MESIF / MOESI 协议:状态机 + RFO 握手,保证单地址一致
        ↓
④ 协议握手太耗时 → Store Buffer(隐藏写延迟)、Invalidate Queue(加速 ACK)
        ↓
⑤ Buffer 造成跨地址操作顺序不可预测(内存一致性模型问题)
        ↓
⑥ 硬件提供屏障指令(MFENCE / DMB / LOCK)
        ↓
⑦ C++ std::memory_order 把顺序需求声明为契约,编译器按架构生成屏障
        ↓
核心原则:
  - 单地址正确性 → 永远由 MESI 保证
  - 跨地址顺序   → 由 memory_order / 屏障约束
  - 性能与顺序的权衡 → 声明越弱越快,责任越在程序员
```

**各协议一句话**:

- **MESI**:E 状态让独占行写入免广播
- **MESIF**:F 状态指定共享副本中的转发者(优化),可丢失,内存兜底
- **MOESI**:O 状态允许脏数据共享,免除写回,但 O 承担回写责任绝不可丢
- **RFO**:一切跨核写入的握手原语,伪共享与锁竞争开销的本质
- **Store Buffer / Invalidate Queue**:隐藏协议延迟,引入乱序,催生内存屏障
- **memory_order**:屏障需求的语言级声明,x86 上大部分"免费",ARM 上按单付费
