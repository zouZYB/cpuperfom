# 测试结果分析

数据：`build/bench.json`（282 个用例 × 3 次重复），机器 AMD Ryzen 7 7800X3D（Zen4）、
Windows 11、MinGW GCC 16.1、`-O3`、缓冲区 4KB 页对齐。
分析脚本：[scripts/analyze.py](scripts/analyze.py)（原始输出 `build/analysis.txt`）。
逐场景的源码/汇编/数据对照见 [CODE-COMPARISON.md](CODE-COMPARISON.md)。

---

## 0. 方法与可信度

**频率标定**：Windows 没有 `perf`，无法直接读 PMU。用两条"延迟已知的依赖链"标定运行频率
（`scripts/clock_probe.cpp`）：`add` 链按 1 cycle/级、`imul` 链按 3 cycle/级，两法偏差 <0.7%，
结果 **5.02 GHz**（单线程睿频）。下文所有 `cycles` 都由 `ns × 5.02` 换算，属于推断值，
但两法互相印证，量级可靠。

**统计口径**：每个用例 3 次重复取中位数；CV 中位数 **0.70%**，P90 **3.1%**，
仅 1 个用例 CV 达 56.9%（`NormalizeSoa/auto_native/4M`，三次为 938µs / 940µs / 2074µs，
中位数不受影响，判断为系统瞬时干扰）。

**结论强度**：大于 5% 的差异可认为是真实的；小于 2% 的差异在本环境下无法区分。

## 1. 总览：SIMD 收益的分布

231 个"非标量"用例相对标量的加速比：

| 统计量 | 值 |
|---|---|
| 最小 | 0.45×（N=1 的 tiny add） |
| P25 | 1.24× |
| **中位数** | **2.74×** |
| P75 | 3.86× |
| 最大 | 20.60×（dot @1K） |

各内核的**最好成绩**（不限规模）：

| 内核 | 最佳加速 | 来自 | 机制 |
|---|---|---|---|
| dot | **20.60×** | avx2 @1K | 标量是延迟链，SIMD 是吞吐 |
| int8 dot | **19.44×** | avx512 @4K | 位宽利用率 + widen/madd |
| dot_f64 | 10.34× | avx512 @1K | 同上，通道数减半 |
| relu | 8.34× | auto_native @1K | 纯带宽，8B/元素 |
| normalize_soa | 7.95× | avx512 @1K | sqrt/div 吞吐 |
| saxpy | 7.80× | auto_native @1K | 纯带宽 |
| add | 6.88× | avx512 @1K | 纯带宽 |
| add_f64 | 3.80× | avx512 @1K | 通道数减半 |
| normalize_aos | 2.88× | auto_native @4M | 排列指令胜 gather |
| gather | 1.05× | avx512 | 延迟受限，ISA 无效 |

## 2. 核心发现：收益由带宽层级决定，而不是指令宽度

把 `add` 沿内存层次展开（各档取该档最佳实现，12 B/元素最小访存）：

| 规模 | 层级 | 标量 cyc/元素 | SIMD cyc/元素 | 有效带宽 | B/cycle | 加速 |
|---|---|---|---|---|---|---|
| 1K | L1 | 1.11 | **0.16** | 373 GB/s | 74.4 | 6.88× |
| 64K | L2 | 1.19 | 0.39 | 155 GB/s | 30.9 | 3.08× |
| 4M | L3 | 1.30 | 0.50 | 120 GB/s | 23.9 | 2.58× |
| 32M | DRAM | 1.41 | 1.14 | 53 GB/s（含 RFO 71） | 10.6 | 1.24× |

三层结论：

1. **L1 内能吃到 6–7 倍**，对应 74 B/cycle。按 x86 常见的 2×32B 载入 + 1×32B 存储
   （≈96 B/cycle）估算，达到上限的 **77%**——剩下的损失来自循环开销与端口调度。
   若只用手写 avx2 这一档口径，则是 340 GB/s ≈ 68 B/cycle。
2. **每降一级，有效带宽腰斩**：L2 约为 L1 的 42%，L3 约 32%，DRAM 只剩 14%（含 RFO 约 19%）。
   SIMD 指令数减少了 4–16 倍，但访存字节一个不少，所以带宽一饱和，加速比就贴着带宽比走。
3. **DRAM 段所有 ISA 收敛**（add：sse41 1.11× / avx2 1.13× / avx512 1.16×）。
   此时代码用 128 位还是 512 位几乎无关紧要——**该换算法、分块或减少访存，而不是换指令**。

平台的 DRAM 饱和度可以用两个"纯流式"用例验证：

- `saxpy@32M`：12 B/元素（x 读、y 读+写，无 RFO），实测 **83.9 GB/s**，
  与双通道 DDR5-5200 的理论 83.2 GB/s 基本一致 → **已打满**；
- `add@32M`：写目标是全新数组，write-allocate 多出一次 RFO（16 B/元素），
  实测 65 GB/s（约 78%）→ 4 条流比 3 条流更难跑满，这是正常现象。

## 3. 逐内核解读

### 3.1 逐元素：add / saxpy / relu

三者都是"无依赖、纯带宽"，但加速比不同，原因只在每元素字节数：

| 内核 | B/元素 | 1K 加速 | 32M 加速 | 说明 |
|---|---|---|---|---|
| add | 12（+RFO） | 6.88× | 1.24× | 2 读 1 写 |
| saxpy | 12（无 RFO） | 7.80× | 1.96× | y 先读后写，省掉 RFO |
| relu | 8（+RFO） | 8.34× | 1.45× | 1 读 1 写，字节最少 |

`relu` 的加速比最高不是因为它"更 SIMD"，而是因为它的**算术强度最低、每元素流量最小**，
标量版本同样受 1 元素/cycle 的限制，SIMD 一次处理 8–16 个元素就能拿满约 7.8 元素/cycle。

### 3.2 归约：dot / dot_f64——这里藏着最大的坑

`dot` 出现了全场最大的反差：

- **标量 20.6× 的落后**：标量版本被编译成一条**串行 `addss` 依赖链**（反汇编确认：
  `movss / mulss / addss`，累加器只有一个），每元素 ≈ **2.87 cycle**，正是 FADD 的延迟。
  标量不是"慢在指令数"，而是"慢在延迟"。
- **自动向量化在这里彻底失效**：`auto_native` 的 dot 只有 **0.81×**（比标量还慢）。
  反汇编显示它确实把乘法和载入向量化了（`vmovups zmm` / `vmulps`），
  但归约仍被展开成**一串串行 `vaddss`**（`vshufps` 抽 lane → 逐个 `vaddss` 到同一寄存器）：
  每 16 个元素仍要走 16 级依赖链，外加 shuffle 开销，所以比标量还慢。
  **浮点归约不允许重排**，编译器只敢做"向量乘 + 标量加"。
- **手写 4 累加器把延迟完全藏起来**：0.14 cycle/元素（约 7.3 元素/cycle），
  相对标量 **20.6×**——这个数字超过 8 宽，正是因为它优化的是"延迟"而不是"指令数"。

推论：**热点求和/点积一律不要指望自动向量化**，手写多累加器，或换成
`std::reduce`（并行版）/ oneDNN / Eigen 之类已经处理好的库。

`dot_f64` 同理，但因 fp64 通道减半，1K 只有 10.3×（而不是 20×）。

### 3.3 int8 点积：19.4×，位宽利用率的胜利

- 标量：2.18 cycle/元素（`movsx` + `imul` + `add` 链）。
- SIMD：0.11 cycle/元素（≈ 9 元素/cycle）。
- 加速 19.4×，甚至超过 16 宽——因为标量版本还要付符号扩展与整数乘法的代价。

AVX2 的实现每个 32 字节做 2 次 `vpmovsxbw` + 2 次 `vpmaddwd` + 2 次 `vpaddd`；
如果换成 AVX-512 VNNI（`vpdpbusd`）还能再省掉 widen，收益会更高。**低精度场景是 SIMD 最划算的地方。**

### 3.4 布局：SoA 7.6× vs AoS 1.1×，且自动向量化反杀手写

| 版本 | 1K | 64K | 4M |
|---|---|---|---|
| normalize_soa（手写 avx512） | 7.95× | 7.64× | 7.78× |
| normalize_aos（手写 avx2） | 1.11× | 1.11× | 1.13× |
| normalize_aos（auto_native） | 2.76× | 2.83× | 2.88× |

- **SoA 版本稳定 7.6–7.9×**，且不随规模衰减（sqrt/div 计算密集，不是带宽受限）。
- **手写 AoS 只有 1.1×**：反汇编显示它按预期退化成"3 次 gather + 标量写回"，
  gather 与写回把收益全部吃掉。
- **auto_native 的 AoS 却是手写的 1.8 倍**：反汇编显示编译器**没有用 gather**，
  而是用 `vpermd` / `vpermt2ps` 这类跨 lane 排列指令，把交错的 xyz 直接重排成 SoA 再算。
  这说明：**同一件事换一种向量化策略，结果差 2.6 倍**，手写 intrinsics 不一定比编译器聪明。

结论：**先改数据结构（AoS→SoA），再谈 intrinsics**。这是本组测试里"投入产出比最高"的一条。

### 3.5 gather：1.04×，SIMD 在这里无能为力

| 规模 | 标量 cyc/元素 | 最佳 SIMD cyc/元素 | 加速 |
|---|---|---|---|
| 4K | 2.35 | 2.25 | 1.05× |
| 64K | 3.17 | 3.06 | 1.04× |
| 1M | 3.18 | 3.06 | 1.04× |

随机索引让每次访问都变成一次"独立的小事务"，吞吐由**未命中延迟 / 并行度（MLP）**决定，
而不是指令宽度。即便 AVX2/AVX-512 有 gather 指令，实测也只和标量打平——
gather 的微码代价 + 缓存行随机性把宽度优势抵消了。遇到这种访问模式，
正确的动作是**换算法/换布局（排序、分桶、预取、转置）**，不是换 ISA。

### 3.6 双精度与小规模

- `add_f64@1K` 3.80× vs `add@1K` 6.88×：**约一半**，与 fp64 通道数减半完全吻合。
  `dot_f64` 10.3× vs `dot` 20.6× 也是同一比例。
- **小 N 会亏本**：N≤3 时 SIMD 只有 0.45–0.68×（函数调用 + 尾部分支 + 启动开销），
  拐点在 **N≈7–8**，N=16 约 2.5×，N=33 约 3.6×。这与"一次迭代要 30–40 个元素才摊平开销"
  的经验一致——**短循环（如 3×3 卷积的小内层）向量化前先量一下**。
- **未对齐的代价比想象小**：4K 规模下 off=0 为 3.24×，off=1..3 为 2.85–2.93×，约 **−12%**；
  64K 规模下 avx512 为 −5~−10%，avx2 基本无影响。现代 `loadu/storeu` 在 L1 内跨 cache line
  才付明显代价，"必须 32 字节对齐"的教条在吞吐型代码里已不成立。

## 4. 宽度效率：128 > 256 > 512（Zen4 特有）

`效率 = 加速比 / 理论宽度`（>100% 说明基线是延迟受限，不是吞吐受限）：

| 内核 @1K | sse41 (4) | avx2 (8) | avx512 (16) |
|---|---|---|---|
| add | 85% | 78% | 43% |
| saxpy | 79% | 90% | 48% |
| relu | 85% | 74% | 51% |
| normalize_soa | 93% | 95% | 50% |
| dot（基线延迟受限） | 263% | 258% | 129% |
| int8 dot @4K（基线延迟受限） | 242% | 238% | 121% |

规律很清晰：**128 位几乎线性（79–93%），256 位在带宽型内核上掉到 74–95%，
512 位只剩 43–51%**。原因是 Zen4 的 512 位执行是"256 位数据通路双泵"：
一条 512 位指令占两个周期，L1 的 32B/周期端口没有变宽，所以 512 位只是"少发指令"，
不增加字节吞吐。实测 avx512 相对 avx2 的额外收益：逐元素 0–46%（中位约 6%），
与理论宽度翻倍相去甚远。**换 Intel Sapphire Rapids 会得到不同曲线——ISA 收益必须实测。**

## 5. 自动向量化 vs 手写：分工非常明确

同宽度对比（耗时比，<1 表示自动更快）：

| 内核 | auto_sse2 / 手写 sse41 | auto_native / 手写 avx512 |
|---|---|---|
| add / saxpy / relu | 0.95–1.05 | 0.98–1.01 |
| normalize_soa | 0.97–1.10 | 1.01–1.04 |
| gather | 1.03 | 1.00 |
| **dot** | **10.6–11.4** | **14.9–25.5** |
| **dot_f64** | **3.8** | 5.5–10.9 |
| **int8 dot** | 3.2 | 3.5 |
| **normalize_aos** | 1.2 | **0.56（自动快 1.8×）** |

三条可操作的结论：

1. **规则逐元素循环不用手写**：`-O3 -march=native` 与手写 intrinsics 差距在 ±5% 内
   （auto_native vs avx512 只有 ±2%），维护成本却低一个数量级。
2. **归约必须手写或用库**：编译器受浮点语义约束，自动版本比手写慢 10–25 倍，
   甚至比标量还慢（0.81×）。
3. **特殊布局让编译器先试**：AoS 上编译器用排列指令打赢了"手写 gather"1.8 倍。
   手写前先看优化报告/反汇编，确认编译器到底做了什么。

## 6. 测量本身的坑（已修复，但值得记录）

第一版数据里 AVX-512 时快时慢、64K 档位甚至掉到比标量还慢（0.93×），排查后定位为
**数组页内偏移效应**：三个数组若页内偏移不同，Zen4 的 512 位路径吞吐掉到约 1/3，
而 256 位不受影响：

```
目的数组相对页首偏移   avx2       avx512
0                      5.4 µs     5.6 µs
64                     5.4 µs    15.6 µs
128                    5.3 µs    11.4 µs
512                    5.7 µs     5.4 µs
```

修复方式是把所有缓冲区改为 **4KB 页对齐**（页内偏移一致），数据立刻稳定。
教训：**微基准必须固定内存布局**，否则分配器的随机对齐会被误读成 ISA 差异；
反过来，生产代码里"为什么同一个内核换个分配路径慢 3 倍"也可能是同一类效应。

## 7. 行动清单

1. **先量再改**：用 Roofline 判断是"算不动"还是"喂不饱"。本机分界点：L1 内可期望 5–8×，
   L2 3–4×，L3 2–3×，DRAM 1.1–2×。
2. **减少字节比换指令更值**：AoS→SoA、合并流、去掉 write-allocate（非临时存储）、
   数据压缩到 int8/fp16，这些动辄 2–8×，且不挑 CPU。
3. **归约手写 4 累加器**：延迟链是标量归约的唯一瓶颈，一条改动 10–20×。
4. **热点逐元素交给编译器**：`-O3 -march=native` + 检查优化报告即可，
   不要为了 1–2% 手写几百行 intrinsics。
5. **小 N 直接标量**：N<8 向量化净亏，N<64 收益有限，先测再改。
6. **别为 gather/随机访问写 SIMD**：1.04× 不值得，换数据结构。
7. **ISA 宽度按平台选**：Zen4 上 AVX-512 只值 ~10%，Intel SPR 上可能值更多；
   用运行期分发（本项目 `dispatch.cpp` 的做法）而不是 `-march=native` 硬编码。
